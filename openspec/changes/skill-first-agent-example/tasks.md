- [x] 9.3 Run the pack with a skill it was not written for — author one throwaway skill with instructions, one resource and one script — and record whether the run followed it, at which step it stopped, and what it reported as unavailable when the deployment withheld a capability. - [x] 9.4 Measure each named strategy against the pack: `GOAP`, `UTILITY`, `HYBRID`, and `SUPERVISOR` with a note that the platform routes it to the GOAP algorithm, recording steps selected, whether it terminated on the skill's stated criteria, and model calls consumed. Write the results into `docs/07-runtime.md`, including the fact that no strategy other than GOAP had ever been run in this repo before this box. Two assertions the delta requires and this box was missing: a strategy must never change what a pack is allowed to do, so the tier verdict, the lifecycle exclusions and the registered tool set have to be identical under all four strategies — a declaration blocked under GOAP is blocked under UTILITY, and if it is not, that is a reach bug in the planner seam rather than a strategy result; and the report must name the algorithm that actually planned the run, since `SUPERVISOR` routing to the GOAP algorithm is precisely the gap between what a setting sounds like and what it does that a reader otherwise assumes away.
- [ ] 9.5 Verify the iteration story rather than assuming it: a re-plan request appears as its own event in the run record, the replan blacklist is what stops a step re-selecting itself, and a run with no reachable plan reports the goal's unmet preconditions instead of an empty failure. State in the pack's notes that repetition comes from re-planning and `canRerun`, since the format has no loop construct. Distinguish a step excluded by lifecycle from a step merely absent from the plan — the report says `excluded`, not `absent` — because that difference is the whole difference between a policy at work and a capability that never existed, and collapsing the two sends a reader to look in the wrong place.
